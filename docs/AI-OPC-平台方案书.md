## 1. 项目定位与故事主线

### 1.1 定位（一句话）

> **FITSOLO = AI × OPC（品牌名已确认）。**
> OPC = Online Personal Coach（线上私人教练）。
> 我们不是"又一个健身 App"，也不是"又一个 AI 聊天框"，
> 而是把一位真实私教（你）的**决策经验 + 真实学员数据**，
> 用 AI 复制成**人人请得起的 24 小时在线私教**。

### 1.2 为什么是现在（机会窗口）

| 要素 | 现状 |
|---|---|
| 信任与流量 | 已有 20 万+ 粉丝，自带获客入口，冷启动成本低 |
| 数据资产 | 大量真实私教学员：体测、方案、打卡、结果全程留痕 |
| 技术成熟度 | 大模型让"个性化对话 + 结构化方案"成本骤降 |
| 行业痛点 | 真人私教贵且不可规模化；健身 App 只有模板、没有监督和个性化 |
| 竞争空白 | "AI 生成方案"与"真人教练经验"目前是分开的，我们把两者焊死 |

### 1.3 故事五幕（网站首页叙事结构）

1. **起点**：一个教练，20 万粉丝，上千名真实学员——手里有别人没有的两样东西：**信任** 和 **真实训练数据**。
2. **痛点**：真人私教贵、排期少、没法覆盖所有人；健身 App 给的是通用模板，练着练着就放弃。
3. **解法**：AI + OPC——把教练的决策经验变成三条智能体流水线：**先体检开方、再盯你执行、最后按数据调整**。每个学员都像有一个 24 小时在线的私教。
4. **证据**：过去学员的真实数据（脱敏后）就是"实验报告"——**基线、方案、过程、结果**四件套全程留痕，可回放、可复现。
5. **愿景**：一个人人请得起的 AI 私教工作室。方案不是拍脑袋，而是**数据驱动、结果可复现**。

### 1.4 核心差异化（竞争对比）

| 对比维度 | 传统私教 | 健身 App | 通用 AI 助手 | 我们（AI + OPC） |
|---|---|---|---|---|
| 个性化 | 高，但贵 | 低（模板） | 中（泛泛而谈） | 高（按你的数据开方） |
| 规模化 | 差 | 强 | 强 | 强 |
| 监督执行 | 强 | 弱（无教练） | 无 | 强（打卡闭环） |
| 动态调整 | 强 | 无 | 无 | 强（按打卡数据调） |
| 真实结果背书 | 有但不可复制 | 无 | 无 | **有 + 可复现** |

### 1.5 一句话话术（给老师 / 投资人）

> "我过去三年靠**真人私教**服务了上千名学员，验证了方法和结果；
> 现在我用 **AI** 把这套方法和真实数据规模化，
> 让 20 万粉丝里每一个想改变的人，都请得起一个私人教练。
> 这不是概念，是已经跑通的结果 × 可复制的技术。"

## 2. 目标用户与核心场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 |
|---|---|---|
| 主画像：职场减脂族 | 25-40 岁，久坐，有消费能力，没时间没专业知识 | 减脂、塑形、瘦身，被监督着练 |
| 次级：增肌男性 | 20-35 岁，想系统增肌/负重训练 | 科学训练计划 + 蛋白粉等补剂指导 |
| 次级：产后/轻运动人群 | 30-45 岁女性，担心强度和安全 | 温和方案、安全边界、异常预警 |
| 潜在：案例围观者 | 粉丝里还没下单的人 | 看到"可复现的真实结果"才信任 |

### 2.2 核心场景（用户旅程）

1. **获客**：粉丝从短视频/图文进入官网 → 看到真实案例回放 → 免费体测。
2. **转化**：体测 → AI 生成个性化方案（免费版给简化版）→ 引导升级会员拿完整方案 + 监督。
3. **留存**：每日打卡 → 进度看板 → 连续打卡激励 → 每周总结。
4. **增值**：平台期/出差/伤病 → 智能指导动态调方案 → 必要时人工教练介入。
5. **口碑**：完成周期后生成"我的结果报告"（可脱敏授权展示）→ 反哺获客。

## 3. 产品定义：三个智能体

### 3.1 总览

| 智能体 | 代号 | 角色 | 一句话 |
|---|---|---|---|
| ① 做方案 | Planner | 诊断 + 开方 | "先体检，再开方" |
| ② 打卡监督 | Checker | 盯执行 | "教练盯着你练" |
| ③ 智能指导 | Coach | 动态调整 + 答疑 | "随时调整，不让你白练" |

三个智能体不是三个独立功能，而是一个**闭环状态机**：

```
用户体测
   │
   ▼
[① Planner] 生成个性化方案 ──► 方案库
   │                                │
   │                                ▼
   └──────────────► [② Checker] 每日打卡（训练/饮食/体重/睡眠）
                          │
                          ▼
              [③ Coach] 分析打卡偏差 → 调整方案 / 答疑
                          │
                          └──► 每周总结 → 回写方案 → 回到 ②
```

### 3.2 智能体 ①「做方案」Planner（引流 + 成交）

**目标**：根据用户身体参数 + 近期一周数据 + 期望目标，生成一份个性化、可解释的分阶段方案。

**输入字段（体测问卷 + 设备数据）**：

| 类别 | 字段 | 来源 |
|---|---|---|
| 基本信息 | 性别、年龄、身高、体重 | 手动 |
| 身体成分 | 体脂率、肌肉量、内脏脂肪、基础代谢（如有） | 体脂秤导入或手动 |
| 围度 | 腰围、臀围、胸围、臂围、腿围（可选） | 手动 |
| 近期数据 | 近 7 天体重/体脂趋势、平均步数/活动量、睡眠时长 | 运动手表（手动填或截图识别） |
| 目标 | 减脂 / 塑形 / 瘦身 / 增肌；期望周期（如 8 周） | 手动选择 |
| 约束 | 每周可训练天数、可用的器械（健身房/居家）、饮食偏好、伤病史 | 手动 |
| 承诺 | 是否愿意使用营养代餐（蛋白粉/代餐奶昔） | 手动 |

**输出方案结构**：

```json
{
  "profile": { "目标": "减脂", "周期周数": 8, "阶段数": 2 },
  "stages": [
    {
      "阶段": 1, "周次": "1-4", "阶段目标": "适应期：建立训练习惯，制造热量缺口",
      "训练": { "每周次数": 4, "力量": ["深蹲", "俯卧撑", "划船"], "负重建议": "...", "有氧": "..." },
      "营养": { "每日热量目标": 1650, "蛋白质": 110, "代餐建议": "早餐代餐奶昔 1 份 + 训练后蛋白粉 1 勺", "时机": "..." },
      "恢复": { "睡眠": "≥7h", "饮水": "..." }
    }
  ],
  "风险提示": ["膝关节旧伤，负重深蹲改为箱式深蹲", "若头晕/心悸请停止并就医"],
  "为什么": ["你的 BMI 26.3、体脂 32%，以减脂为目标，建议先制造 300-500 kcal 缺口…"]
}
```

**关键要求**：

- **可解释**：每个建议带"为什么"（基于用户数据的推理），这是信任和可复现性的基础。
- **可量化**：训练次数、负重范围、热量、蛋白质、代餐用量都是具体数字，不是"适量"。
- **有边界**：异常数据（如 BMI > 35、有伤病、疑似进食障碍）自动降级为"温和方案 + 建议咨询专业人士"。
- **结构化输出**：所有方案走 JSON Schema 校验，保证机器可读、可回放、可对比。

### 3.3 智能体 ②「打卡监督」Checker（留存 + 续费）

**目标**：让用户"每天被盯着"，形成习惯和持续付费的理由。

**打卡内容（每日表单，尽量 1 分钟完成）**：

| 类别 | 字段 |
|---|---|
| 训练 | 是否完成今日训练 / 实际内容 / 主观强度（1-10） |
| 饮食 | 是否按方案执行 / 蛋白质是否达标 / 代餐是否使用 |
| 身体 | 体重、体脂（可选，建议每周 3 次以上） |
| 状态 | 睡眠小时、精力（1-10）、是否不适 |

**监督与激励机制**：

- 每日提醒（App/微信/邮件，MVP 先做网页提醒 + 浏览器通知）。
- 连续打卡计数 + 里程碑（7/14/21/30 天）成就体系。
- 漏打卡策略：当日 23:00 前补卡；连续 3 天未打卡触发 Coach 主动关心（而非指责）。
- 每周自动生成《周报》：完成率、体重/体脂趋势、下一周调整建议。

### 3.4 智能体 ③「智能指导」Coach（增值 + 口碑）

**目标**：基于打卡数据动态调整方案 + 回答用户问题，让方案"活"起来。

**触发场景**：

- 用户主动提问（"今天加班没练怎么办？""代餐可以换成正餐吗？"）。
- 打卡数据异常（体重连续 2 周不动 → 平台期应对；连续 3 天没打卡 → 关心 + 简化任务）。
- 周报生成时自动给出下一周调整建议。
- 用户上传训练照片/视频（MVP 可选）→ 基础动作姿态反馈。

**调整规则示例（写进知识库，保证可复现）**：

| 信号 | 规则 |
|---|---|
| 体重连续 2 周无变化且打卡完成率高 | 下调热量 100 kcal 或增加 1 次有氧（二选一，避免同时改） |
| 连续 3 天未打卡 | 主动问候 + 临时简化方案（减 1 个动作） |
| 疲劳度高（连续 3 天精力 ≤ 4/10） | 本周减 1 次训练，增加睡眠建议 |
| 用户报告膝盖/腰部不适 | 替换对应动作 + 提醒就医，停止加重建议 |

**边界**：不诊断、不开药、不保证结果；医疗类问题一律引导就医。

### 3.5 闭环的意义（对商业模式）

打卡数据回流 → 方案越调越准 → 用户结果更好 → 案例数据更丰富 → 新用户转化更高。这是产品的**数据飞轮**，也是"真实可复现"的技术基础。

## 4. 数据资产与"真实可复现"策略

### 4.1 我们手里有什么数据

| 数据 | 说明 | 用途 |
|---|---|---|
| 学员档案 | 年龄/性别/身高/体重/体脂/围度/目标 | 画像与匹配 |
| 体测记录 | 周期性的身体成分变化 | 结果证明 |
| 方案记录 | 给每位学员开过的训练/营养方案 | 知识库来源 |
| 打卡记录 | 训练/饮食/体重/睡眠的过程数据 | 监督与调整依据 |
| 结果记录 | 周期结束后的最终数据 + 对比照 | 案例包装 |

> **核心原则**：这些数据必须先**脱敏**（去标识化：姓名/头像/手机号等一律移除，只保留统计特征）才能进入产品演示和案例展示。

### 4.2 可验证案例"四件套"（每个上首页的案例必须齐全）

```
1. 基线（Before）：体测数据 + 目标 + 起始日期
2. 方案（Plan）：AI/教练开出的具体方案（可回放）
3. 过程（Process）：打卡时间线（完成率、体重/体脂变化曲线）
4. 结果（After）：最终数据 + 周期长度 + 对比
```

- **只有前后对比照、没有过程数据的案例，不上首页**——因为不可复现，也经不起追问。
- 案例页展示形式：时间轴 + 曲线图 + "点击回放当时的方案"按钮。

### 4.3 cohort（同批学员）统计口径

用"一组人"的平均结果替代"一个人"的爆款结果，既真实又有冲击力：

> 示例话术："2025 年 100 名减脂学员，8 周训练营，平均体脂率下降 4.8%，其中 78% 完成全程打卡，76% 完成率达标。"

**口径要求（避免虚假宣传）**：

- 必须注明：样本量、周期、纳入标准（如"完成 ≥ 60% 打卡"）、统计时间。
- 不做"幸存者偏差"：不把未完成学员偷偷剔除；要么如实标注"仅统计完成全程者"。
- 保留原始统计脚本/数据（脱敏后），任何质疑都能复查——**可复现 = 敢于公开方法**。

### 4.4 方案回放：可复现性本身就是产品

- 网站提供"方案回放"演示：输入某案例的**原始参数**，AI 复现出**当年开出的那份方案**。
- 这直接证明：方案不是随机生成的，而是**由输入数据决定的确定性流程**（规则 + 知识库约束，而非纯自由发挥）。
- 技术实现：Planner 使用"知识库规则 + 结构化输出"组合，同一输入在版本不变时产出同一方案（确定性优先）。

### 4.5 免责声明与医疗边界（必须，且是加分项）

- 页面/方案底部固定声明：**"AI 方案仅供参考，不构成医疗诊断或治疗建议；结果因人而异；如有疾病请遵医嘱。"**
- 异常数据（BMI ≥ 35、报告伤病/慢性病/孕期等）自动降级处理，并建议线下专业人士。
- 敢划边界 = 专业可信，反而提升转化。

## 5. 商业模式（建议，评审时确认）

### 5.1 三层结构

| 层级 | 内容 | 定价思路 |
|---|---|---|
| 免费层（引流） | 体测 + 简化版方案（1 周示例） | 0 元，换取手机号/微信 |
| 会员层（主力） | 完整方案 + 打卡监督 + 智能指导 + 周报 | 订阅制，如 ¥99/月 或 ¥299/季 |
| 增值层（高客单） | 人工教练复查 / 平台期 1 对 1 干预 | 按次或按周期，如 ¥499/期 |

### 5.2 定价原则（评审时定）

- 参考竞品：Keep 会员（¥25/月左右）、真人私教（¥300-800/节）。
- 我们的锚点：**"一个真人私教的价格，买到 24 小时 AI 私教 + 真人兜底"**，定价区间建议 ¥99-199/月。
- 首期可做"粉丝内测价"（20 万粉丝本身就是第一批种子用户）。

### 5.3 数据飞轮（护城河）

```
学员越多 → 脱敏数据越多 → 知识库/规则越准 → 方案效果越好 → 案例越强 → 转化越高
```

这是竞品（无真实教练数据）很难短期复制的壁垒。

## 6. MVP 范围（B 阶段做什么）

### 6.1 P0：必须做（验收标准 = 能现场演示一条完整闭环）

1. **官网单页**：故事五幕 + 三智能体介绍 + 案例回放入口。
2. **Planner Demo**：用户填体测表单 → 生成完整方案（可下载 .md / 打印另存为 PDF）→ 方案带"为什么"。
3. **Checker Demo**：每日打卡表单 + 进度看板 + 连续打卡计数。
4. **Coach Demo**：对话窗口，能基于打卡数据回答"今天练不练/怎么调"并给出调整。
5. **案例回放**：预置 2-3 个脱敏案例，一键回放"当时开的方案"。
6. **数据**：本地存储（JSON/SQLite）跑通闭环；`.env` 管理 API Key。

### 6.2 P1：暂不做（明确砍掉，避免返工）

- ❌ 真实支付/订单系统（先用"预约/意向表单"代替）
- ❌ 微信/短信推送（先用浏览器通知 + 邮件占位）
- ❌ 体脂秤/手表 API 自动导入（先手动填 + 截图识别占位）
- ❌ 视频动作分析、生成式教练形象（二期再说）
- ❌ 多租户/复杂权限（单教练起步）

### 6.3 MVP 演示脚本（老师验收用）

> 打开官网 → 看故事 → 点开"案例回放"看真实数据 → 进入"做方案"填一份体测 → 生成 8 周方案 → 模拟打卡 3 天 → 问 Coach"今天加班没练怎么办" → Coach 给出调整 → 完成。

## 7. 技术架构（B 阶段落地依据）

### 7.1 仓库结构（monorepo，便于上 GitHub 演示）

```
fitsolo-ai/
├─ docs/                  # 方案书 + 教练知识库文档
│  └─ AI-OPC-平台方案书.md
├─ web/                   # Next.js：官网 + 产品页 + 三个智能体界面
│  ├─ app/                # 页面路由
│  ├─ components/         # 组件
│  └─ ...
├─ agents/                # 三个智能体的核心逻辑（与界面解耦）
│  ├─ planner/            # ① 做方案
│  ├─ checker/            # ② 打卡监督（规则 + 激励）
│  ├─ coach/              # ③ 智能指导（调整规则 + 对话）
│  ├─ knowledge/          # 教练知识库（规则、动作库、营养库）
│  └─ schemas/            # JSON Schema（输入/输出校验）
├─ data/                  # 脱敏示例数据 + 案例
├─ .env.example           # 环境变量模板（绝不提交真实 Key）
├─ .gitignore
└─ README.md              # 项目故事 + 架构图 + 运行说明
```

### 7.2 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 前端/官网 | Phase 1：零依赖静态站；Phase 2 迁 Next.js (React + TS) | SEO 好、生态成熟、适合内容引流 |
| 智能体编排 | LangChain（轻量）或直接 LLM API + 函数调用 | MVP 不追求重框架，先跑通闭环 |
| 输出格式 | JSON Schema 强校验 + 知识库规则 | 保证方案"确定性可复现" |
| 数据存储 | MVP: SQLite/JSON；生产: PostgreSQL + 加密 | 渐进式，不返工 |
| 部署演示 | Vercel（官网） | 免费、快，适合交作业 |
| 版本管理 | Git + GitHub | 故事与代码一起展示 |

### 7.3 三个智能体的实现思路（关键设计）

**核心思想：规则优先，AI 辅助，输出强约束。**

- Planner：
  1. 表单数据 → 规则引擎算出基础参数（BMI、热量缺口、蛋白质目标、训练频率）。
  2. 知识库匹配动作库/营养库 → 组装阶段方案。
  3. LLM 只负责"用用户能懂的语言写为什么 + 润色"（或直接模板生成，确定性更强）。
  4. 输出过 JSON Schema 校验 → 存入方案库。
- Checker：
  1. 纯规则：打卡表单 → 计算完成率/连续天数/里程碑。
  2. 提醒与周报用模板生成，不依赖 LLM（省成本、稳定）。
- Coach：
  1. 信号检测（规则）：从打卡数据检测平台期/漏卡/疲劳/不适。
  2. 命中规则 → 从"调整规则表"取对应调整 → 更新方案。
  3. 自由提问 → LLM 基于"当前方案 + 打卡数据 + 知识库"回答，并限定边界（不诊断/不开药）。

### 7.5 教练知识库设计（核心资产，文本先行）

把"你的方法论"沉淀为结构化文档，作为 AI 的约束源：

```

```

## 8. 合规与隐私（必须做，不能省）

### 8.1 法律定位

- 身体成分、体重、健康相关数据属于**敏感个人信息**（《个人信息保护法》第 28 条），处理需**单独同意**。
- 面向用户提供"个性化健康/运动建议"属于服务，不等于医疗；但**必须**避免医疗诊断表述。

### 8.2 必做清单（MVP 就做）

| 项 | 做法 |
|---|---|
| 用户同意书 | 注册/体测前弹窗：收集哪些数据、用途、如何删除 |
| 最小化收集 | 只收达成目标必需的字段，不做无边界采集 |
| 加密 | 传输 HTTPS；数据库中的敏感字段加密存储 |
| 访问控制 | 用户只能看自己的数据；教练可看脱敏汇总 |
| 导出与删除 | 用户可一键导出/注销删除（个保法权利） |
| 案例授权 | 展示任何学员案例前必须有书面授权 + 脱敏 |
| 免责声明 | 方案页/官网固定展示（见 4.5） |

### 8.3 设备数据导入（体脂秤/手表）注意

- 若未来接厂商 API：需要用户授权该厂商数据共享，并在产品内说明"仅用于生成方案，不转卖"。
- MVP 用手动填写/截图识别即可，不碰授权问题，先跑通。

## 10. 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 虚假宣传被质疑 | 夸大案例、无过程数据 | cohort 口径 + 四件套 + 方案回放 |
| 医疗责任 | 用户受伤/投诉 | 边界声明 + 异常降级 + 转人工/就医 |
| 数据合规 | 敏感数据泄露 | 最小化收集 + 加密 + 同意书 + 删除权 |
| AI 幻觉 | 方案里出现错误动作/剂量 | 知识库约束 + 规则优先 + 人工抽检 |
| 技术返工 | MVP 架构过重 | 先 Demo 后重构，接口与界面解耦 |
| 依赖单一 | 只靠一个 LLM 供应商 | 封装 Provider 层，可切换 |
